# C# 계산 동작 보존과 Python 성능 비교 계획

작성일: 2026-10-21. 상태: **별도 재현 기준 구현·동일 조건 성능 측정 완료 / 최적화 없음**.
대상은 InventoryEngine `inventory_engine_dev`다. [재현 계약](IO_LEGACY_PYTHON_REFERENCE_CONTRACT.md)에 따라
기존 개선형과 분리한 기준 구현을 추가했다. FSN·운영 Gate·DB·Runtime Binding은 유지한다.
아래 최적화 항목은 여전히 계획이다. [실제 측정 보고서](IO_LEGACY_PSI_PERFORMANCE_BASELINE.md)에서는
16품목 계산 1.390ms/141.220ms, 파일 저장 포함 전체 9.237ms/161.743ms로 현재 Python이 느렸다.
측정 조건별 21개 표본과 전체 결과 일치를 확인했으며 성능 개선으로 표현하지 않는다.

## 1. 목표와 현재 확인 범위

목표는 C#의 PSI·발주 계산 동작을 Python에서 재현한 뒤, 같은 결과를 내는 실행 방법 중 더 빠른 방법을 고르는 것이다.
현재 Python의 개선된 업무 규칙과 Legacy 동작을 한 번에 섞어 바꾸지 않는다.
성능 때문에 입력 검증이나 게시 차단을 없애는 것도 범위 밖이다.

- [실제 실행 기록](evidence/legacy-native-execution-verification-20261021.json): 원본 7파일·계산/DTO 21구간을 DB 없이 실행했다.
  C# 대응 20사례·29회 계산과 기존 Golden의 불일치는 0건이다. 전체 운영 프로그램 검증은 아니다.
- [Python 비교 결과](evidence/legacy-native-python-comparison-20261021.json): 발주 시점·Lot·도착 주차·Forecast 부족 이월 등이 다르다.
  기존 개선형 Python과 C# 시간을 바로 비교하면 서로 다른 계산을 비교하게 된다.
- [기존 참조기](../../tests/reference/legacy_csharp/README.md)는 정합성 확인용이다.
  실행 명령에 `-c Release`가 없고 계산 전용 반복 측정·Warm-up·백분위 기록도 없다.
  앞선 테스트 전체 소요시간이나 컨테이너 빌드시간을 C# 계산시간으로 쓰지 않는다.
- 원본 `RootIO/Program.cs:292`의 PROD 경로는 이미 품목별 `Parallel.ForEach`를 사용한다.
  Python만 병렬화하고 C# 직렬 경로와 비교해 Migration 성과로 주장하지 않는다.

현재 **별도 재현 Python의 C# 대비 시간 차이는 실측했으며, 최적화 후 개선량은 미측정**이다.
현재 SDK에서 원문 구간을 실행한 수치와 기존 운영 서버/배포본의 처리시간은 구분한다.

## 2. 선택지와 권장 방향

| 선택지 | 장점 | 비용·주의점 | 권고 |
| --- | --- | --- | --- |
| Python 단순 이식 | C# 동작을 읽고 비교하기 쉽다 | Python으로 옮긴다는 이유만으로 빨라지지는 않는다 | 동등성 기준 구현으로 먼저 사용 |
| Python 배열 계산 + Numba JIT | 업무 계약은 Python에 두고 반복 계산을 컴파일할 수 있다 | 새 선택 의존성·최초 컴파일·수치 검증이 필요하다 | 병목 확인 후 우선 실험 |
| Python 조립 + C# 계산 Adapter | 확인된 계산 구간을 그대로 유지하기 쉽다 | .NET 빌드/배포와 전달 비용을 함께 관리한다 | Python 최적화가 목표를 못 맞추면 대안 |

권장은 **Python 동등성 기준 구현 → 기준 측정 → 병목만 최적화 → 결과·성능 재대조**다.
JIT 경로가 C#보다 빠를 것이라고 미리 약속하지 않는다. 느리면 그 결과도 남긴다.
C# Adapter를 선택해도 품목·주차마다 호출하지 않고 묶음 전달 비용을 측정한다.
GPU·모델 변경·대규모 자원 관리 고도화는 우선 범위에 넣지 않는다.

## 3. 결과를 유지하며 줄일 수 있는 작업

아래는 코드 구조에서 찾은 **최적화 후보**이지, 실측으로 확정한 병목이나 개선량은 아니다.

1. **주차별 반복 탐색을 준비 단계로 옮긴다.**
   `BufferPSIObject.cs:32`의 `SetBucket`은 주차마다 수요·정책·입고 목록을 훑고 첫 일치 행을 선택한다.
   인덱스를 재사용하되 중복 행의 첫 일치·기간 경계·BaseMonth 의미를 보존한다.
   여러 행을 임의로 합산하는 것은 최적화가 아니라 계산 변경이다.
2. **입고 도착 주차를 미리 찾는다.**
   `BufferPSIObject.cs:110`의 `SetDuein`은 주문마다 전체 주차를 탐색한다.
   검증된 Calendar에서 일자→주차 매핑을 준비하되 기간 밖 입고·LT 0·포함 경계를 보존한다.
3. **계산 중 객체·날짜·문자열 생성을 줄인다.**
   수량·정책·도착 위치를 배열로 준비하고 결과 행과 JSON은 계산 바깥에서 조립한다.
   불변 입력만 공유하고 재고·미도착 주문·정책 상태는 품목/후보별로 분리한다.
4. **시간 순서는 유지하고 독립 품목·후보만 병렬화한다.**
   전주 EOH가 다음 주 BOH이므로 주차를 독립 작업처럼 병렬화하지 않는다.
   CPU 제한·Worker 수를 양쪽에서 맞추고 결과 및 집계 순서도 고정한다.
5. **계산 최적화와 저장 최적화를 구분한다.**
   기존 공유 입력·압축·분할 저장은 재사용하고 전체 후보의 필요한 PSI·선정 근거는 남긴다.
   후보 수나 결과 행을 줄인 시간을 동일 결과의 계산 개선으로 적지 않는다.

## 4. 계산 동등성의 선행 조건

- C# `double`과 현재 Python `Decimal`은 같은 수치 표현이 아니다.
  재현 경로의 숫자 표현·연산 순서·`Math.Round` 중간값 반올림을 먼저 고정한다.
  소수·Lot·ROP 직전/일치/직후·LT 0·월/주 경계·기간 밖 주문을 추가 검증한다.
- 근사 연산·합산 순서 변경·`fastmath=True`는 기본적으로 허용하지 않는다.
  성능 때문에 발주량이나 적격 여부가 바뀌면 동등성 합격으로 처리하지 않는다.
- 주차별 BOH·입고·수요할당·미충족량·EOH·PO·누적 PO와 발주/도착일을 대조한다.
  공통 필드의 값·순서와 기존 ID·Hash를 재사용한다. 서로 다른 JSON 구조의 파일 Hash 일치를 요구하지 않는다.
  각 원본 출력 파일 Hash는 별도로 보존하며 추가 식별자를 불필요하게 만들지 않는다.
- 수량·상태·일자·경계 판단의 기준과 허용 오차는 측정 전에 정한다. 나중에 오차를 넓혀 합격시키지 않는다.
- 전체 정책 선정의 동등성은 `SVC_LV` 집계·최종 Winner·그룹→품목 전개 확인 뒤에만 주장한다.
  제한된 PSI 계산 성능 비교는 이와 구분해 먼저 진행할 수 있다.

## 5. 공정한 성능 비교

**비교군:** C# 원문 Release / Python 동등성 기준 / Python 단계별 최적화.
현재 개선형 Python은 필요하면 별도 참고군으로 두며 Legacy 동등성 성과에 섞지 않는다.

- 같은 장비·OS/아키텍처·CPU/메모리 제한에서 직렬군과 동등 병렬군을 각각 측정한다.
  C#은 제한된 컨테이너, Python은 제한 없는 호스트에서 실행하는 식으로 비교하지 않는다.
- 품목·후보·주차 수, Calendar, BOH, 수요·공급, LT, Lot, 정책과 입력 순서를 고정한다.
  Golden은 정확성 확인용이며 처리량 측정에는 별도 크기 고정 자료를 사용한다.
  32/32/88 후보군은 실제 실행 수를 명시하고 중복 제거 조건도 양쪽에서 같게 적용한다.
- 단일 품목에서 소규모 묶음으로 늘린다. JIT 준비 후 계산시간과 최초 호출시간을 분리한다.
  컴파일·컨테이너 기동·입력 파싱·직렬화·Hash·저장을 계산시간에 몰래 넣거나 빼지 않는다.
- 반복마다 동일 입력에서 재고 상태를 초기화한다. 이전 반복의 EOH·주문을 이어 쓰지 않는다.
  실제 출력을 소비·검증해 컴파일러가 계산을 제거하지 않게 한다.
- Warm-up·독립 프로세스·측정 반복 수, 실행 순서와 Seed를 사전 기록한다.
  중앙값·P95·편차·처리량·최대 메모리를 남기며 한 번의 최저시간으로 판단하지 않는다.
- `입력 준비 / PSI 계산 / 평가·선정 / 직렬화·Hash / 저장 / 전체 처리`를 구분한다.
  DB 없는 1차 비교는 DB/네트워크 제외를 명시한다. 전체 비교는 출력·검증·저장 책임을 맞춘다.
  확인하지 못한 C# 단계는 0이 아니라 `비교 범위 밖`으로 남긴다.

- 속도비 = `C# 시간 / 비교 구현 시간`.
- 시간 단축률 = `(C# 시간 - 비교 구현 시간) / C# 시간 × 100`.
- 속도비 1 미만 또는 음수 단축률은 느려진 결과로 기록한다. 같은 측정 구간의 중앙값을 비교한다.

입력·출력·기존 Hash, Commit/작업 트리, C# 원문 지문, 구현·의존성 Version,
Release 옵션, 장비, 명령, 측정 원문과 제외 범위를 함께 남긴다.
보고서는 `동일 장비의 C# 원문 PSI 구간 대비`로 범위를 제한하며 운영 DSIO 전체 성능으로 일반화하지 않는다.

## 7. 남은 작업 순서

**현재 기준선 — C# 재현 경로의 계산 계약과 기준 구현 · InventoryEngine**

- 현재 개선형 Python과 분리해 발주 순서·Lot·시간·수치 규칙을 재현한다. FSN·운영 Gate는 유지한다.
- 진단용 기준 구현과 실제 C# 구간 출력 대조는 완료했다. 전체 엔진·최종 정책 선정 동등성은 미검증이다.

**현재 기준선 — 비교 입력 확정·최적화 전 기준 측정 완료 · InventoryEngine Offline**

- Release C#과 동등 Python을 같은 조건에서 측정했고 136개 결과 파일의 바이트 일치를 확인했다.
  속도 차이는 확인했지만 세부 병목의 기여도는 아직 프로파일로 분해하지 않았다.

**1. 비용 분해 후 실행 방식 선택·단계별 재검증 — 다음/후속 직렬 작업 · InventoryEngine**

- 먼저 비용을 프로파일로 확인한 뒤 인덱스·배열·JIT·C# Adapter의 적용 범위를 선택한다.
  이번에는 어떤 계산 최적화도 수행하지 않았다.
- 매 단계의 결과 동일성과 더 빠르거나 느린 이유를 확인한 뒤 실제 수치를 이 양식에 기록한다.
  서비스·전체 선정 Source 조사는 독립 진행 가능하지만 최종 선정 성능 주장은 그 확인 뒤에 한다.
- DB 변경·실제 발주·공용 Runtime 배포는 포함하지 않는다. Commit/Push도 이번 검토 범위가 아니다.

## 공식 기술 자료와 검토 경계

- [Numba Performance Tips](https://numba.readthedocs.io/en/stable/user/performance-tips.html):
  실제 입력 프로파일링·루프 컴파일·병렬화·fastmath의 수치 의미 변경을 확인했다. 예시 배수를 IO 성과로 인용하지 않는다.
- [BenchmarkDotNet Good Practices](https://benchmarkdotnet.org/articles/guides/good-practices.html):
  Release·디버거 없는 실행, 환경별 결과의 제한, 계산 제거 방지 기준을 확인했다.

`oma-architecture`·`oma-qa`의 선택지 비교와 검증 범위 분리를 적용했다.
계획 작성 시에는 제품 코드를 변경하지 않았으며 이후 별도 진단용 재현 구현을 추가했다.
이후 로컬 전용 이미지에서 성능 Benchmark를 수행했다. 호스트 의존성 설치·DB Write·배포·Commit/Push는 수행하지 않았다.
