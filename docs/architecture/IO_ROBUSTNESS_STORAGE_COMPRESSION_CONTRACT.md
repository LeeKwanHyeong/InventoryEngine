# 분할 증적의 성능 비교와 무손실 압축 계약

## 1. 범위와 변경하지 않는 기준

InventoryEngine `inventory_engine_dev`의 로컬 수작업 입력을 대상으로 한다. 원 계산 결과·전체 후보·주차별 PSI·행동·Guard 증적을
모두 보존한다. FSN 설정·운영 Gate·재고 수식·정책 선정 규칙·공식 경로/기간/Seed·DB·공용 Runtime은 변경하지 않는다.
저장량 감소는 증적 생략·요약만 보존·후보 축소·소수 반올림으로 달성하지 않는다.

- [기존 강건성 계약](IO_CATALOG_ROBUSTNESS_CONTRACT.md)의 20,000,000,000 Byte 원문 예산,
  파일당 128,000,000 Byte와 호출당 3,600초 기준을 유지한다. 압축을 이유로 원문 예산을 늘리지 않는다.
- 이 단계는 성능 비교 기준과 선택 가능한 V2 저장기를 구현한다. 서비스 전체 활성화·전역 디스크 예약/시간 취소·청소 정책을
  이미 구현했다는 뜻은 아니다. 벤치마크의 단일 Worker 시간 제한/보수적 용량 사전 확인은 로컬 측정 도구에만 적용된다.
- 기준 Git HEAD는 `99f2f12`와 기존 미커밋이며, 실제 비교는 소스 파일 지문을 별도로 고정한다. 설치·배포·Commit/Push는 하지 않는다.

## 2. 닫힌 비교 사양

[기계 판독 사양](data/robustness-storage-benchmark-v1.json)은
[계약 코드](../../src/dsio_inventory_engine/inventory_contracts/robustness_storage.py)의 고정 값과 정확히 같아야 한다.
사양 Hash는 `f96f089823d5c747b5cb09da516fa87ef4b0d7460f2d5033c28c44d68a11f06f`다.

- 2055-01-04 W0·DSE/C100/V101/ITEM-A/EA의 기존 수작업 Fixture를 사용한다. 주어진 한 NOMINAL 경로
  `HAND-CATALOG-PATH`/Seed 71·65주·PRICE_BASE·REVIEW를 유지한다. 원 부모 분류와 전체 Catalog는 변경하지 않는다.
- ABC/XYZ 32개·LEGACY_STYLE 32개·WIDE_REFERENCE 88개 각각을 `JSON_V1`과 `GZIP_V2`로 3회 비교한다.
  총 18회이며 홀수 반복은 JSON 먼저, 짝수 반복은 Gzip 먼저 실행한다. 모든 반복은 CPU Worker 1개로 직렬이다.
- 각 반복은 새 프로세스와 비어 있는 전용 폴더를 사용한다. OS 파일 캐시를 비운 실험은 아니며 조회는 쓰기 후의 캐시 영향을 받는다.
  실행 전에 사양·구현 파일 지문을 보존하고, 각 Worker와 종료 시점에 같은 소스인지 검사한다.
- 각 방법의 입력 Assembly·실현 경로·부모 분류·전체 Catalog·결과·Leaf Hash는 두 저장 방식과 반복에서 같아야 한다.
  모든 후보는 성공·65주를 보존하는 수작업 사례다. 일반 Writer의 후보 실패 보존 규칙을 바꾸지 않는다.
  예측/정책의 우열을 판정하거나 공식 강건성 비교를 실행하는 절차가 아니다.
- 측정치는 준비, 계산, 게시 전 실제 재생 검증, 재생 검증을 제외한 저장, 원문 무결성 조회, 저장 접근을 제외한 재생 검증으로 나눈다.
  저장 전체/조회 전체 시간도 별도 기록하지만 겹치는 값을 다시 더하지 않는다. 저장에는 직렬화·압축·Byte/Hash 검사·Metadata 준비가 포함된다.
  무결성 조회에는 원문 동등성 비교도 포함되며, 이를 단순 디스크 읽기 시간으로 표시하지 않는다.
- 메모리는 프로세스 전체의 절대 최대 RSS Byte다. Mac/Linux 단위를 정규화하고 단계별 할당량 또는 Python 객체 크기라고 표현하지 않는다.
  Python·OS·CPU 아키텍처·zlib 버전을 함께 기록한다. 3회 미만은 `SMOKE_ONLY`이며 성능 향상 근거로 승격하지 않는다.
- 18회가 모두 있어야 비교 완료다. 누락·중복·입력/결과 불일치·Gate 변경이 있으면 성공 집계를 만들지 않는다.
  각 단계 중앙값·실제 파일 크기·최대 RSS를 보고한다. 압축에 따른 용량 감소를 수학적 전략의 계산 속도 향상으로 주장하지 않는다.

## 3. Hash와 파일 참조 V2

기존 계산 문서의 `contract_id`/`contract_version`/`content_hash`와 최종 Result Hash를 유지한다. 압축은 계산 계약이 아닌 물리 저장 계층이다.

| 필드 | 의미 |
|---|---|
| `content_hash` | 기존 봉인 계산/증적 문서의 논리 Hash |
| `byte_count` | 정규 JSON UTF-8와 마지막 LF를 포함한 원문 Byte 수 |
| `raw_sha256` | 위 원문 바이트 전체의 SHA-256 |
| `stored_byte_count`, `stored_sha256` | 실제 Gzip 파일의 크기와 바이트 SHA-256 |
| `storage_version` | `2.0.0` |
| `encoding`, `codec_version`, `compression_level` | `GZIP`, `RFC1952-DEFLATE-V1`, `1` |

V2 참조는 이 10개 필드만 허용한다. 코덱/버전·크기·Hash는 강제 검증하며 Boolean을 정수로 인정하지 않는다.
같은 원문이라도 압축 파일과 원문의 물리 Hash는 다르다. 저장 Manifest/Receipt는 V2 물리 참조를 포함하므로 V1과 Hash가 달라도 되며,
이를 계산 결과 Hash 변경으로 혼동하지 않는다. 입력 문서·Leaf·원 계산 결과는 복원 후 동일해야 한다.

## 4. 호환성과 Append-only 동작

[선택 가능한 압축 저장기](../../src/dsio_inventory_engine/infrastructure/robustness_compression.py)는
[기존 V1 저장기](../../src/dsio_inventory_engine/infrastructure/robustness_artifacts.py)의 파일 안전성·배타적 게시·`fsync`를 재사용한다.

- 신규 V2 객체는 `object-{content_hash}.json.gz`, 기존 V1 객체는 `.json`이다. 입력/Leaf/완료 포인터 이름은 유지한다.
  새 Reader는 V1·V2를 모두 읽지만 과거 V1 Reader가 V2를 읽는다고 주장하지 않는다.
- 기존 V1 객체가 있으면 검증 후 V1 참조를 그대로 재사용한다. 기존 파일을 압축 파일로 덮거나 삭제하지 않는다.
  완료된 V1 실행의 Receipt/Manifest는 새 Reader로 읽어도 변하지 않는다.
- 부분 V1 실행은 기존 Input/Leaf 포인터를 보존하고 나머지 V2 조각을 이어 저장할 수 있다. Manifest는 혼합 참조를 명시한다.
- 신규 Gzip은 mtime 0·낮은 압축 수준으로 작성한다. 이미 유효한 Gzip이 있으면 재압축하지 않아 Python/zlib 업그레이드로 재요청이 충돌하지 않게 한다.
  같은 논리 포인터의 다른 참조는 여전히 충돌이다. 서로 다른 구/신 Writer의 동시 포인터 게시도 조용히 교체하지 않는다.
- Writer→실제 Run 조립→완료 Manifest→Reader/복구까지 동일한 Repository 인터페이스로 연결한다.
  V2는 명시적 선택이며 기존 서비스의 기본 저장기나 공용 Runtime을 자동 전환하지 않는다.

## 5. 손상·복원 상한과 용량 산정

- 실제 파일 크기·물리 Hash를 먼저 확인한 뒤 복원한다. 원문 출력은 선언된 크기+1 Byte까지만 생성하고 상한 초과를 거부한다.
  선언된 원문 크기와 실제 복원 크기도 모두 128,000,000 Byte 이하여야 한다. 복원 후에야 JSON을 해석한다.
- 잘린 프레임·CRC 오류·다중 Gzip Member·뒤따르는 바이트·잘못된 원문 Hash·비정규/중복 Key JSON을 차단한다.
  Symlink·FIFO·디렉터리·바뀐 Root와 잘못된 경로는 기존 저장기와 같이 거부한다.
- 복원된 원문을 완전히 검증한 뒤 기존 논리 Hash를 확인한다. 압축 참조가 손상됐다고 V1이나 다른 파일로 자동 전환하지 않는다.
  누락/손상된 완료 실행은 성공으로 바꾸지 않는다. 중단 복구 시에도 원 Source·후보·실제 Guard/PSI 재생 검증은 유지한다.
- 원문 예산은 각 물리 객체의 원문 크기를 한 번씩 더하고 포인터 원문을 추가한다. 같은 폴더의 멱등 재요청은 파일을 늘리지 않지만,
  서로 다른 반복 폴더에 만든 사본은 각각 예산에 포함한다. 압축 파일 크기로 원문 예산을 할인하지 않는다.
- 디스크 점유는 반복 완료 시 남아 있는 전체 파일과 압축 Metadata·포인터를 합산한다. 알 수 없는 파일이나 임시 파일이 남으면
  비교를 실패시킨다. 성공 시 잔여 임시 파일은 0개지만, 쓰기 도중의 순간 최대 임시 공간까지 측정한 것은 아니다.
  측정 도구의 사양/소스/반복 보고서도 전체 예산 점검에서 제외하지 않는다. 원문 예산·물리 점유량·복원 메모리는 서로 다른 값이다.

## 7. 2026-10-20 실제 수작업 측정

18회 모두 `COMPLETE_COMPARISON`을 충족했다. 세 방법별 원 입력·부모 분류·전체 Catalog·결과·Leaf Hash가
두 저장 방식과 세 반복에서 일치했다. 32후보는 매회 2,080 PSI Row, 88후보는 5,720 PSI Row를 보존했다.
소스 375개 파일의 지문 Hash는 `54ea62606113faeed3cab43b6870c4df748f7110ff1b42c17c2d5ab295974637`이다.
Python 3.12.10 / Darwin arm64 / zlib 1.2.12 환경이며, 다른 회귀 테스트와 겹치지 않게 직렬 측정했다.

파일 크기는 객체·포인터를 포함한 반복 완료 시의 점유량이며 MB는 1,000,000 Byte다.
RSS는 각 방식의 세 반복 중 최댓값이며 MiB는 1,048,576 Byte다. 두 단위를 혼용하지 않는다.

| 방법 | 후보 | V1 파일 MB | V2 파일 MB | 용량 감소 | 최대 RSS V1 → V2 MiB |
|---|---:|---:|---:|---:|---:|
| ABC·XYZ | 32 | 50.805 | 3.884 | 92.36% | 852.69 → 1,894.20 |
| LEGACY_STYLE | 32 | 50.801 | 3.884 | 92.35% | 887.97 → 858.02 |
| WIDE_REFERENCE | 88 | 139.081 | 10.584 | 92.39% | 1,606.73 → 1,454.30 |

다음은 각 단계의 3회 중앙값(초)이다. 저장은 게시 전 재생 검증을 뺀 값이며,
마지막 재생 검증은 저장소 접근을 뺀 값이다. 단계 전체를 단순 합산해 호출 시간을 추정하지 않는다.

| 방법 / 저장 방식 | 준비 | 계산 | 게시 전 재생 | 저장 | 무결성 조회 | 재생 검증 |
|---|---:|---:|---:|---:|---:|---:|
| ABC·XYZ / V1 | 0.108 | 4.419 | 4.985 | 1.633 | 1.216 | 5.162 |
| ABC·XYZ / V2 | 0.108 | 4.393 | 5.048 | 1.782 | 1.260 | 5.121 |
| LEGACY_STYLE / V1 | 0.111 | 4.388 | 5.155 | 1.687 | 1.265 | 5.072 |
| LEGACY_STYLE / V2 | 0.108 | 4.364 | 5.073 | 1.772 | 1.244 | 5.036 |
| WIDE_REFERENCE / V1 | 0.120 | 12.499 | 14.304 | 4.779 | 3.604 | 13.943 |
| WIDE_REFERENCE / V2 | 0.121 | 12.055 | 13.689 | 4.926 | 3.538 | 13.731 |

- 압축은 실제 점유량을 줄였지만 저장 중앙값은 약 3.1~9.1% 늘었다. 계산 코드가 같으며 관측된 시간 차이를
  수학적 전략의 속도 개선이나 통계적 우월성으로 주장하지 않는다. 새 프로세스라도 쓰기 후 OS 캐시가 남는 조건이다.
- ABC·XYZ/V2 첫 반복의 RSS 1,986,215,936 Byte는 나머지 두 반복보다 높았다. 원인을 이번 실험에서 확정하지 않았고,
  값을 제외하거나 재측정값으로 대체하지 않았다. 압축으로 메모리가 일관되게 줄었다고 결론 내리지 않는다.
- 전체 측정 폴더는 230파일·777,238,696 Byte다. 압축 원문·포인터·측정 Metadata까지 포함한 원문 예산은
  1,444,270,123 Byte이며, 가장 큰 원문 객체는 24,502,038 Byte다. 원문 20GB/파일 128MB 기준을 넘지 않았다.
  이는 한 수작업 경로의 18회 측정이지 공식 전체 경로의 예상 용량 합격이 아니다.
- 복원 메모리·전체 결과 보유와 반복 재생 검증은 남아 있다. 다음 성능 개선은 공통 입력 중복과 반복 준비/직렬화,
  빠른 조회와 실제 재생 검증의 책임 분리를 먼저 다루며, 재검증을 생략해 수치를 개선하지 않는다.
- 새 검증 62건을 포함한 전체 회귀는 **1,527 passed / 9 skipped / 669 subtests passed**(529.72초)다.
  기존 Starlette 경고 3건과 미수행 도구·개별 반복·보고서 Hash는
  [검증 기록](evidence/robustness-storage-compression-20261020.json)에 구분한다.
